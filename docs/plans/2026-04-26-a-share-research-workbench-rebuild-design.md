# A 股个人研究工作台重构策划案

## 1. 背景与判断

当前仓库来源复杂，混合了数据抓取、特征加工、机会雷达、Streamlit 展示、邮件推送，以及对 `TradingAgents-CN` 的集成尝试。经过这轮梳理，可以确认几个事实：

- 现有项目还没有形成稳定可复用的“日常使用闭环”。
- 历史设计发生在半年前，前提已经变化，继续在旧骨架上补丁式维护，收益低于重构收益。
- `TradingAgents` / `TradingAgents-CN` 可以提供参考，但都不适合直接作为本项目新的核心底座。
- 当前最有价值的方向不是“自动生成更多结论”，而是“建立信任”。

因此，本项目不建议继续沿旧框架扩展，而应重构为一个目标单一、边界清晰的个人研究工作台。

## 2. 产品目标

### 核心目标

构建一个面向个人日常使用的 A 股研究工作台，服务 10-30 只重点跟踪标的，重点解决两个问题：

1. 这些股票是否正在接近值得考虑的买点。
2. 最新的公司/财报/基本面信息，是否在强化或削弱这个买点。

### 第一优先级

- `证据透明`：每个结论都必须能回溯到原始数据、触发条件和评分过程。
- `历史验证`：每类信号都必须能查看过去的样本表现、命中情况和失效情况。

### 低优先级

- 长篇自然语言解释
- 全市场自动筛选
- 多市场统一覆盖
- 复杂多 Agent 协作链路
- 自动交易

## 3. 用户场景

用户每天打开系统，优先不是“发现所有机会”，而是“复查自己关心的股票”。

首页应优先回答：

- 哪些自选股已经进入或接近观察区间。
- 这些股票当前触发了哪些买点条件。
- 最近是否出现了会改变判断的公司级信息。
- 过去类似情形在历史上表现如何。

单票页再进一步提供：

- 价格位置与技术形态证据
- 基本面与财报证据
- 外部信息摘要
- 历史同类信号回放
- 可选解释层（默认折叠）

## 4. 范围边界

### 第一版必须支持

- 市场：A 股
- 覆盖对象：10-30 只重点跟踪标的
- Watchlist 管理
- 买点触发检测
- 基本面/公司事件过滤
- 历史验证页面
- 简洁可读的研究工作台 UI

### 第一版明确不做

- 港股 / 美股
- 通用投研平台
- 完整多 Agent 编排
- 大规模自动候选池生成
- 聊天式智能问答主界面
- 券商联动 / 自动下单

## 5. 重构原则

1. 不再把 `TradingAgents-CN` 作为主项目内核依赖。
2. 不再让 LLM / Agent 直接担任信号真相来源。
3. 任何信号都必须由可复算规则和可回放数据支撑。
4. 先做“研究工作台”，再做“推送系统”。
5. 先做“少量标的深服务”，再做“全市场筛选”。

## 6. 对开源项目的借鉴策略

### 6.1 Qlib

借鉴内容：

- 研究流程分层
- 特征 / 标签 / 回测结构
- 历史验证与可复现思路

用途：

作为本项目“可信研究底座”的主要参考。

### 6.2 FinRL-X / FinRL-Trading

借鉴内容：

- 模块边界
- 数据、策略、验证、执行分层
- 生产化研究思路

用途：

辅助设计信号引擎和验证链路，不直接作为 UI 框架。

### 6.3 TradingAgents

借鉴内容：

- analyst role 的拆分方式
- 单票研究的结构化输出思路
- 可选解释层

用途：

仅作为“分析解释层”的候选参考，不作为主骨架。

### 6.4 TradingAgents-CN

借鉴内容：

- A 股数据接入与产品形态
- 个股详情、任务反馈、配置中心等交互经验

用途：

参考其 A 股产品经验，但不直接继承其系统结构，也不把其代码作为长期依赖。

### 6.5 FinRobot / FinNLP

借鉴内容：

- equity research / valuation 报告结构
- 新闻、财报、文本信息处理思路

用途：

作为信息层和解释模板参考。

## 7. 建议的新架构

项目重构为四层：

### 7.1 Ingestion

负责抓取和标准化原始数据。

数据来源建议按优先级组织：

- 行情 / K 线 / 技术数据：A 股主行情源
- 财报 / 估值 / 关键财务字段：主财务源
- 公司事件 / 公告 / 新闻：公司级信息源

产出统一写入研究数据库，不直接耦合 UI。

### 7.2 Research Store

统一存储：

- watchlist
- symbol 基础信息
- 行情历史
- 特征快照
- 基本面快照
- 事件信息
- 信号结果
- 历史验证结果

现有 Supabase / Postgres 可以继续保留，作为第一版研究存储层。

### 7.3 Signal Engine

采用“先触发，再过滤”的结构：

- 触发层：价格接近区间、回踩支撑、均线接近、突破回踩等
- 过滤层：估值、财报质量、公司事件、基本面趋势
- 输出层：结构化结论，不直接输出模糊自然语言

输出字段建议包含：

- signal_state
- trigger_type
- trigger_score
- valuation_score
- quality_score
- event_risk_score
- conviction_score
- reasons
- invalidation_conditions

### 7.4 Research UI

UI 只做研究展示，不承担分析计算。

建议页面结构：

- 首页：watchlist 总览、接近买点列表、近期变化
- 单票页：价格证据、基本面证据、事件信息、历史验证
- 历史验证页：按信号类型查看过去表现
- 配置页：标的列表、阈值、数据刷新状态

默认信息密度要高，但解释层折叠。

## 8. 首页信息结构

首页不应先展示复杂图表，而应先展示决策相关信息。

建议分成四块：

1. `今日重点变化`
   - 哪些股票状态发生变化
   - 新进入观察区间 / 脱离区间 / 基本面变化

2. `接近买点`
   - 当前最值得复查的 5-10 只股票
   - 直接展示距离区间、触发类型、评分变化

3. `基本面/公司事件提醒`
   - 财报、预告、回购、分红、管理层变化等

4. `历史验证摘要`
   - 当前策略近一年同类触发的样本数、胜率、平均后续表现

## 9. 可信度设计

这是项目成败关键。

每个信号必须可展开查看：

- 触发该信号的原始价格数据
- 使用的技术位和阈值
- 参与过滤的基本面字段
- 最近事件数据
- 历史同类案例数量
- 历史表现分布

系统不应该优先说“建议买入”，而应该优先说：

- 为什么它进入观察区间
- 为什么这个机会值得或不值得跟
- 历史上类似情况通常怎样

## 10. 第一版技术建议

### 保留

- Python 作为分析主语言
- Supabase / Postgres 作为研究数据库
- 当前已能复用的数据抓取脚本和字段定义

### 简化

- UI 先保留单一前端，不并行维护 Streamlit + 另一套大前端
- LLM 层只作为可选增强，不作为第一版主依赖
- 不在第一版引入复杂消息队列和多服务编排

### 不建议

- 继续深度耦合 `external/TradingAgents-CN`
- 直接把单独的 `TradingAgents-CN/` 仓库并入主项目
- 让多 Agent 架构主导产品结构

## 11. 旧仓库迁移策略

建议把现有内容拆成三类：

### A. 直接保留

- 有明确产出的抓数脚本
- Supabase 表结构与字段定义
- 已验证有效的雷达评分逻辑

### B. 重写但保留思路

- Streamlit 首页结构
- 雷达展示方式
- 邮件推送与定时工作流

### C. 暂时废弃

- 子模块式 `TradingAgents-CN` 深度集成
- 以多 Agent 为中心的主流程
- 与当前产品目标无直接关系的多市场和实验脚本

## 12. 成功标准

重构第一版成功，不是看代码是否更漂亮，而是看是否形成以下闭环：

1. 我每天会打开它。
2. 它能准确告诉我哪些自选股值得今天复查。
3. 每个结论我都能看到证据来源。
4. 我能看到历史上类似情况到底有没有用。
5. 我逐渐愿意依据它安排研究顺序。

## 13. 下一步

在本策划案确认后，再输出正式实施 To-Do，按以下顺序拆分：

1. 新项目模块划分
